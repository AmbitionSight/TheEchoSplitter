# Git 提交规范与分支模型设计

日期：2026-10-03
状态：已批准（待实施）

## 背景与动机

仓库原有 59 个提交，大部分已有 `feat:/fix:/docs:/chore:` 前缀，但存在三类问题：

1. 个别提交无前缀（如 `5d48439 前三关界面优化…`）。
2. 单条提交塞多件事，用"；"拼接不相关改动，主题超长（80+ 字符）。
3. 规范只存在于习惯中，未成文；分支上，日常工作直接提交到 main，`chapter1` 分支已完全合并却仍保留在本地与远端。

本设计确立 develop + main 双轨分支模型、成文提交规范，并对旧历史做一次性清理。

## 分支模型（develop + main 双轨）

- **main**：稳定可玩版本。只在章节完成、回归测试全绿、真机验证过的节点上更新。
- **develop**：日常开发分支，所有日常提交落在 develop。
- **合并**：develop → main 用 `git merge --no-ff`，保留合并节点；main 上按章节/大功能打 tag（`v0.x` 级别）。
- **短期分支**：风险大的单项工作（如某章重构）可从 develop 开短期分支，完成后合回 develop。
- **清理**：删除 `chapter1` 本地与远端分支（无独有提交，已完全合并）。

## 提交信息规范

格式：

```
<type>: <中文主题>

<动机与背景>

<实现要点 / 关键决策>

<测试与验证>
```

- **type 集合**：`feat` `fix` `docs` `refactor` `test` `chore` `ui`（视觉/布局调整）。破坏性变更用 `feat!` / `fix!`。
- **主题**：≤ 32 个汉字，祈使语气，概括"做了什么"。
- **一个提交只做一件事**：多主题必须拆开，禁止用"；"拼接不相关改动。
- **细节进 body**：动机、实现要点、测试情况写在 body，不把主题撑长。
- **引用文档**：涉及设计稿/计划时，body 里给出 `docs/` 下的路径。

## 旧历史一次性清理

原则：改写后 force push（单人单机，无其他克隆）。

- **reword**（只改标题、细节进 body）：无前缀的 `5d48439`，以及主题超长的若干条。
- **拆分**（按文件可分离性逐一判断，纠缠不清的降级为 reword）：
  - ch1 接公共壳那条（5 个主题）；
  - 抽 shell.js + sideview.js 那条；
  - 第二、三间房那条（jump/rope/书档携带/路由/结算入口）；
  - 仪式石双渲染那条（4 个独立修复）；
  - 语音延迟那条（2 个）。
- **实施顺序**：写规范文档并提交 → 改写历史 → force push → 建 develop → 删 chapter1。

## 成文与工具

- 规范全文写入 `docs/CONTRIBUTING.md`。
- CLAUDE.md 加一小节指向该文档（确保今后每个 Claude Code 会话都遵守）。
- 不加 hook/工具强制：零依赖项目，靠文档约束足够。

## 验收标准

1. `git log --oneline` 全部提交符合 type 前缀，主题不超长。
2. 本地与远端均无 `chapter1` 分支；main 与 origin/main 一致。
3. develop 分支存在且与 main 同步，成为日常开发落点。
4. `docs/CONTRIBUTING.md` 存在且 CLAUDE.md 有指向它的引用。
5. 清理后 `npm test` 全绿。
